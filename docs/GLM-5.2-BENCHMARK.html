1 · Total throughput by deployment shape

8K-in / 1K-out, thinking off. Higher is better.

2-node TP16 at concurrency 40 wins on raw throughput (730 tok/s) but uses two nodes — per-node it is 365 tok/s vs 456 tok/s for a single-node TP8. PD (1P+1D) trails on this prefill-heavy profile.

2 · Time-to-first-token (p50) by shape

Same runs. Lower is better.

TP16 c40 delivers both the best TTFT (1.2s) and the best throughput — deep batching across 16 GPUs. PD suffers on TTFT here because prefill hand-off adds queueing at high concurrency.

3 · KV-cache offload to host RAM — engine A/B (single node)

Long-document reuse: 8 users × ~30K-token docs, concurrency 8, re-asked after GPU-pool eviction. Cold = full prefill; Hot = reload from host RAM. Lower is better.

Cold TTFT (full prefill) Hot TTFT (host-RAM reload)

Same hardware, same fp8 KV, same workload — only the offload implementation differs. SGLang HiCache reloads the full 240K-token working set from host RAM (8.1× faster TTFT, log-verified 100% cache hit); vLLM's native OffloadingConnector barely hits (2.5% hit rate). vLLM's documented remedy is the lmcache offload backend (untested — round B).

4 · Why offload pays off on single-node but not on PD

SGLang HiCache, hot-vs-cold speedup of the same experiment run against two deployment shapes.

On PD every request still pays the prefill→decode KV transfer + handshake, which dominates once prefill compute is removed — offload gains vanish (~1.0×). On a single node there is no transfer floor, so the full prefill saving lands (10.4× wall-clock on this working set). Capacity rule: benefit is binary — working set must fit the host pool, or LRU eviction zeroes it.
